# #3 技術深度解析

## 技術亮點回顧

在前兩篇日誌中，我們看到了兩個工具的誕生和整合實施。現在，讓我們深入探討整合過程中的技術亮點和設計巧思。

## 亮點 1：專案探索的迭代式對話

### 問題背景

傳統的 AI 代碼生成工具通常只給 AI 一個需求描述，然後期待它生成正確的代碼。這導致：
- AI 不知道專案現有的類別和方法
- 生成的代碼風格不一致
- 經常使用不存在的依賴
- 需要大量人工修正

### 解決方案：Tool Use API

使用 Anthropic Tool Use API，讓 Claude 像人類開發者一樣**迭代式探索專案**。

```python
async def design(self, requirement_file, project_root, ...):
    messages = []

    # 初始 prompt
    messages.append({
        "role": "user",
        "content": f"請基於需求文件設計系統...\n專案路徑: {project_root}"
    })

    for iteration in range(MAX_ITERATIONS):  # 最多 30 輪
        response = await self.client.messages.create(
            model=self.model,
            messages=messages,
            tools=TOOLS
        )

        # 檢查停止原因
        if response.stop_reason == "end_turn":
            # AI 完成探索
            final_content = response.content[0].text
            break

        if response.stop_reason == "tool_use":
            # AI 請求使用工具
            for block in response.content:
                if block.type == "tool_use":
                    # 執行工具
                    tool_result = self._execute_tool(
                        block.name,
                        block.input,
                        project_root
                    )

                    # 添加工具結果到對話
                    messages.append({
                        "role": "assistant",
                        "content": response.content
                    })
                    messages.append({
                        "role": "user",
                        "content": [{
                            "type": "tool_result",
                            "tool_use_id": block.id,
                            "content": tool_result
                        }]
                    })

    return final_content
```

## 亮點 2：優雅的降級設計

### 問題背景

在企業環境中，系統穩定性至關重要。automation_tool 的整合不能：
- 導致 jira_poller 無法啟動
- 在 API 失敗時中斷工作流
- 讓錯誤難以診斷

### 解決方案：三層降級機制

```python
def _ai_generate_requirements(self, task, feedback):
    """三層降級策略"""

    # 第一層：automation_tool (最佳)
    if self.requirement_analyzer:
        try:
            return self._ai_generate_requirements_with_automation_tool(task, feedback)
        except Exception as e:
            self.logger.error(f"automation_tool 失敗: {e}")
            # 繼續到下一層

    # 第二層：傳統 AI Provider
    if self.ai_provider:
        try:
            return self._ai_generate_requirements_fallback(task, feedback)
        except Exception as e:
            self.logger.error(f"AI Provider 失敗: {e}")
            # 繼續到下一層

    # 第三層：占位符（確保流程不中斷）
    return self._generate_placeholder_requirements(task, feedback)
```

## 亮點 3：異步與同步的優雅橋接

### 問題背景

- jira_poller 是同步代碼（使用 threading, time.sleep）
- automation_tool 使用異步 API（Anthropic SDK）
- Python 不允許在運行中的事件循環創建新事件循環

**錯誤示例**：
```python
# 在同步函數中
result = asyncio.run(async_function())
# RuntimeError: asyncio.run() cannot be called from a running event loop
```

### 解決方案

```python
import asyncio

def _call_async_in_sync(self, async_function, *args, **kwargs):
    """在同步環境安全地調用異步函數"""
    try:
        # 嘗試獲取當前事件循環
        loop = asyncio.get_event_loop()

        if loop.is_running():
            # 已有運行中的事件循環
            # 這種情況下無法使用 asyncio.run()
            self.logger.warning("檢測到正在運行的事件循環，無法使用 automation_tool")
            raise RuntimeError("Cannot use async in sync context")

    except RuntimeError:
        # 沒有事件循環，或上面拋出的異常
        # 安全地創建新事件循環
        result = asyncio.run(async_function(*args, **kwargs))
        return result
```

### 使用方式

```python
# 需求階段
result = asyncio.run(self.requirement_analyzer.analyze(
    requirement=requirement_text,
    project_name=task.key
))

# 設計階段
result = asyncio.run(self.system_designer.design(
    requirement_file=str(req_file),
    project_root=str(project_root),
    output_dir=str(output_dir),
    user_id=task.key,
    project_name=task.key
))
```

### 為什麼這樣設計？

**選項 A：將 jira_poller 改為異步**
- ❌ 大規模重構
- ❌ 可能影響穩定性
- ❌ 與其他同步庫不兼容

**選項 B：將 automation_tool 改為同步**
- ❌ Anthropic SDK 是異步的
- ❌ 無法利用異步優勢
- ❌ 性能下降

**選項 C：橋接層（我們的選擇）**
- ✅ 最小化改動
- ✅ 保持兩邊原有架構
- ✅ 降級處理異常情況

## 亮點 4：Git Worktree 與專案探索的完美配合

### 設計巧思

**關鍵傳參**：

```python
# jira_poller (orchestrator.py)
def _ai_generate_design_with_automation_tool(self, task, req_content, feedback):
    # 獲取當前任務的 Git Worktree 路徑
    project_root = self.current_worktree  # 例如: workspace/unity-wt-AG-123/

    # 傳入 automation_tool
    result = asyncio.run(self.system_designer.design(
        requirement_file=str(req_file),
        project_root=str(project_root),  # ← 關鍵！
        output_dir=str(output_dir),
        user_id=task.key,
        project_name=task.key
    ))
```

**automation_tool 中的使用**：

```python
# automation_tool (system_designer/designer.py)
async def design(self, requirement_file, project_root, ...):
    # project_root 就是 Unity Worktree 路徑

    # 執行工具時使用這個路徑
    def _execute_tool(self, tool_name, tool_input, project_root):
        if tool_name == "get_project_structure":
            return self._get_project_structure(project_root, tool_input)

        elif tool_name == "read_file":
            file_path = Path(project_root) / tool_input['file_path']
            return file_path.read_text()

        elif tool_name == "search_code":
            # 在 project_root 中搜尋
            results = self._search_code(project_root, tool_input)
            return results
```

### 為什麼這樣設計很巧妙？

1. **隔離性**：
   - 每個 Jira 任務有獨立的 Git Worktree
   - AI 探索不會影響其他任務
   - 失敗可以安全刪除 Worktree

2. **並發性**：
   - 可同時處理多個任務
   - 不同 Worktree 互不干擾

3. **可追溯性**：
   - 探索過程的文件讀取都記錄在日誌
   - 可以知道 AI 看了哪些文件

4. **安全性**：
   - AI 只能讀取 Worktree 中的文件
   - 無法訪問其他專案或系統文件

## 亮點 5：反饋循環的自動整合

### 問題背景

人工審批可能會提出修改建議：

```
Jira 評論：
@rejected

請補充以下內容：
1. 需要考慮移動平台的性能差異
2. 應該包含記憶體使用的優化目標
3. 需要說明向下相容性問題
```

**挑戰**：如何讓 AI 看到這些反饋？

### 解決方案：臨時文件

**需求階段**：

```python
def _ai_generate_requirements_with_automation_tool(self, task, feedback):
    # 構建包含反饋的需求文本
    feedback_section = ""
    if feedback:
        feedback_section = f"\n\n## 人工反饋（請根據反饋重新分析）\n{feedback}\n"

    requirement_text = f"""# Unity 開發任務需求
{task.description}{feedback_section}
"""

    # RequirementAnalyzer 會看到反饋
    result = asyncio.run(self.requirement_analyzer.analyze(
        requirement=requirement_text,
        project_name=task.key
    ))
```

**設計階段**：

```python
def _ai_generate_design_with_automation_tool(self, task, req_content, feedback):
    req_file = self.file_manager.get_stage_file_path(task.key, "需求")

    if feedback:
        # 讀取原始需求
        original_content = req_file.read_text(encoding='utf-8')

        # 附加反饋
        temp_content = f"""{original_content}

---

## 人工反饋（請根據此反饋調整設計）

{feedback}
"""

        # 創建臨時文件
        temp_req_file = req_file.parent / f"{req_file.stem}_with_feedback{req_file.suffix}"
        temp_req_file.write_text(temp_content, encoding='utf-8')
        req_file_to_use = temp_req_file
    else:
        req_file_to_use = req_file

    # SystemDesigner 讀取的是包含反饋的文件
    result = asyncio.run(self.system_designer.design(
        requirement_file=str(req_file_to_use),
        ...
    ))

    # 清理臨時文件
    if feedback and temp_req_file.exists():
        temp_req_file.unlink()
```

## 經驗總結

### 成功的關鍵因素

1. **清晰的接口設計**
   - automation_tool 的輸入輸出都是標準格式
   - 便於其他系統整合

2. **優雅降級**
   - 失敗不中斷流程
   - 用戶體驗平滑

3. **充分的日誌**
   - 每個關鍵步驟都記錄
   - 便於診斷問題

4. **保持獨立性**
   - 兩個系統可單獨使用
   - 降低耦合度

5. **實用主義**
   - 選擇快速有效的方案（方案 A）
   - 避免過度工程化

### 遇到的挑戰

1. **異步同步橋接**
   - 挑戰：Python 事件循環限制
   - 解決：檢測並創建新循環

2. **路徑管理**
   - 挑戰：三個路徑概念（automation_tool 路徑、worktree 路徑、輸出路徑）
   - 解決：清晰的命名和文檔

3. **API 速率限制**
   - 挑戰：SystemDesigner 會調用 10-20 次 API
   - 解決：錯誤處理 + 日誌提示

4. **反饋傳遞**
   - 挑戰：如何讓 AI 看到人工反饋
   - 解決：臨時文件附加反饋

### 可改進之處

1. **API 速率限制處理**
   - 當前：失敗後等待用戶重試
   - 改進：自動重試 + 指數退避

2. **工具調用監控**
   - 當前：只記錄總次數
   - 改進：詳細記錄每次調用的時間和內容

3. **反饋質量檢查**
   - 當前：直接傳遞人工反饋
   - 改進：檢查反饋格式，提供改進建議

4. **並發處理**
   - 當前：串行處理任務
   - 改進：支援並發處理多個任務

**測試階段挑戰**：
- 需要創建 Pull Request
- 需要運行測試
- 如何處理測試失敗？

## 結語

- 它會搜尋相關代碼
- 它會閱讀現有實現
- 然後基於理解生成方案

**這就是 Tool Use API 的力量。**

- ✅ 完整的 DevOps 工作流整合
- ✅ 人機協作的最佳實踐

**這只是開始。**

隨著 AI 能力的進步和 Tool Use API 的演進，我相信未來會有更多可能：
- 更深入的專案理解

**讓我們一起期待 AI 輔助開發的未來。**
